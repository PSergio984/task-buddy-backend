# Phone-down timer: sensor feasibility (iOS/Android)

Research for [task-buddy-backend#53](https://github.com/PSergio984/task-buddy-backend/issues/53).
Scope: what sensors/APIs can drive a Dote Timer-style "clock runs only while phone is face-down" focus timer, per platform. Companion repo context: `task-buddy-mobile` is **Expo SDK 58, managed CNG (no `ios/`/`android/` dirs), EAS builds** — so "Expo Go vs dev build" boundaries below apply directly.

## Feasibility matrix

| Capability | Android | iOS foreground | iOS backgrounded / locked | Expo (Go vs dev build) |
|---|---|---|---|---|
| Detect face-down via accelerometer/gravity | ✅ `TYPE_ACCELEROMETER`/`TYPE_GRAVITY` z-sign, no permission | ✅ CoreMotion accel/`CMDeviceMotion` attitude, `UIDevice.orientation == .faceDown` | ❌ callbacks stop when suspended | ✅ Expo Go (`expo-sensors` `Accelerometer`/`DeviceMotion`) |
| Detect "screen covered" via proximity | ✅ `TYPE_PROXIMITY` (near/far, some give cm); **wake-up sensor by default** | ✅ `isProximityMonitoringEnabled` + `proximityState`; **screen auto-blanks when covered (can't be prevented)** | ❌ notifications stop when app backgrounds | ❌ no Expo module; needs dev build (custom module or `react-native-proximity`-style lib) |
| Keep sensing with screen off | ⚠️ Foreground service + `PARTIAL_WAKE_LOCK` works until Doze; in Doze non-wake-up sensors stall, wake-up proximity events still arrive | ❌ app suspends on lock/background | ❌ | ⚠️ dev build (native FGS needed) |
| Retroactively verify phone stayed down while app was suspended | ⚠️ no sensor history API — must keep an FGS alive to observe events live (proximity wake-ups logged w/ timestamps) | n/a | ✅ `CMSensorRecorder.recordAccelerometer` ≤12 h @50 Hz buffered while suspended/killed (iPhone 7+); `CMMotionActivityManager.queryActivityStarting` history | ❌ dev build (no Expo module for sensor recorder) |
| Detect user opened another app mid-session | ✅ `UsageStatsManager` (`PACKAGE_USAGE_STATS` special-access grant) | ✅ `DeviceActivity`/Screen Time API (FamilyControls entitlement, iOS 16+) | ✅ `DeviceActivityMonitor` extension runs outside the app while suspended | ❌ dev build + Apple entitlement approval |
| Timer keeps counting while app closed | ✅ wall-clock anchor (store start timestamp) | ✅ same | ✅ same — compute elapsed on resume | ✅ Expo Go |
| Wake app on a schedule during session | ⚠️ exact alarms limited (1/15 min in Doze); FGS is the reliable route | n/a | ❌ BGTaskScheduler timing is system-chosen; silent push throttled to ~1–2/hr | ⚠️ `expo-background-task` exists but ≥15-min system-chosen cadence — useless for verification |

## 1. Android

**Face-down detection.**
- Accelerometer z-axis sign is the primary signal: Android's coordinate system puts +z "toward the outside of the screen face"; lying flat face-up reads ≈ +9.81 m/s² on z, so face-down ≈ −9.81 m/s². No permission needed — most sensors aren't permission-gated; `ACTIVITY_RECOGNITION` is only for Google Play Services' activity-recognition API (an optional alternative that exposes `STILL`/`TILTING` states, not needed for a flip timer). [Android position sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position) · [Sensors overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview) · [SO: face-up/face-down via inclination](https://stackoverflow.com/questions/14477133/how-to-use-android-sensor-event-to-determine-if-device-is-facing-up-or-down)
- `TYPE_PROXIMITY` adds corroboration ("screen against a surface/in pocket"). Most proximity sensors return cm, some only near/far; some are under-display and show a blinking dot when active. [Position sensors doc](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position)
- Sampling >200 Hz needs `HIGH_SAMPLING_RATE_SENSORS` on Android 12+ — irrelevant here (10–50 Hz suffices). [expo-sensors docs](https://docs.expo.dev/versions/v58.0.0/sdk/sensors/)

**Screen-off / background sensing.**
- Sensor listeners stop when the app is killed; for continuous sensing use a foreground service. On Android 14+ (API 34) every FGS needs a declared `foregroundServiceType` + matching `FOREGROUND_SERVICE_*` permission — there is **no "sensors" type**; realistic fits are `specialUse` (requires Play Console justification) or `health` (needs `HIGH_SAMPLING_RATE_SENSORS` declared or a runtime permission like `ACTIVITY_RECOGNITION`). API 31+ also forbids starting an FGS while the app is in the background → start it at session-start while foreground. [FGS types required](https://developer.android.com/about/versions/14/changes/fgs-types-required) · [Service types](https://developer.android.com/develop/background-work/services/fgs/service-types) · [Background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
- **Doze**: when the device is unplugged + stationary + screen off, Doze ignores app wake locks and suspends non-wake-up sensors — accelerometer events buffer into the hardware FIFO and are only delivered when the SoC wakes (or are lost if no FIFO). `TYPE_PROXIMITY` and `TYPE_SIGNIFICANT_MOTION` are **wake-up sensors by default**, so a "uncovered/lifted" proximity change still fires in Doze — that's the key cheating signal that survives. Battery-optimization whitelisting does *not* restore non-wake-up sensor delivery. [Doze/App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) · [AOSP suspend mode](https://source.android.com/docs/core/interaction/sensors/suspend-mode) · [SensorManager getDefaultSensor](https://developer.android.com/reference/android/hardware/SensorManager) · [SO: Doze + sensor listeners](https://stackoverflow.com/questions/37776309/how-does-doze-mode-affect-registered-listeners-especially-sensor-listeners)

**Platform alternatives.**
- **Health Connect**: health/fitness record types only (steps, HR, sleep…) — no orientation or app-usage data. Irrelevant here. [Health Connect data types](https://developer.android.com/health-and-fitness/health-connect/data-types)
- **Digital Wellbeing** (incl. Pixel's "Flip to Shhh"): no public API.
- **UsageStatsManager**: `PACKAGE_USAGE_STATS` is a special-access permission granted via Settings → "Usage access"; lets the app query which app was foreground — this is how Forest-style blockers detect app-switching on Android. Some OEMs strip the grant UI. [UsageStatsManager](https://developer.android.com/reference/kotlin/android/app/usage/UsageStatsManager) · [Special permissions](https://developer.android.com/training/permissions/requesting-special)

## 2. iOS

**Foreground (works today).**
- `UIDevice.orientation == .faceDown` via `beginGeneratingDeviceOrientationNotifications` — simplest signal, API since iOS 2.0. [SO](https://stackoverflow.com/questions/36097204/how-to-tell-if-the-iphone-is-face-down-or-face-up)
- CoreMotion: raw accelerometer gravity or `CMDeviceMotion.attitude`/`.gravity` — on iOS the reported vector's z-component ≈ **+1 g face-down, −1 g face-up** (opposite sign convention to Android). Quaternion attitude avoids gimbal lock if needed. [SO face-down](https://stackoverflow.com/questions/36097204/how-to-tell-if-the-iphone-is-face-down-or-face-up) · [SO attitude](https://stackoverflow.com/questions/20379830/ios-core-motion-detect-forard-backward-tilt)
- `UIDevice.isProximityMonitoringEnabled = true` → `proximityState` changes + `UIDeviceProximityStateDidChangeNotification`. **Caveat**: covering the sensor *always* blanks the screen — no public API prevents it (fine for our UX — it IS the "face down → screen off" behavior). Verify support by setting then re-reading the property (setter no-ops on devices without the sensor, e.g., iPads). [SO keep-display-on](https://stackoverflow.com/questions/27147847/keep-display-on-when-the-proximity-sensor-is-covered) · [Microsoft Learn/UIDevice docs](https://learn.microsoft.com/en-us/dotnet/api/uikit.uidevice.proximitymonitoringenabled)

**Backgrounded / locked — the crux.**
- Everything live **stops**: app suspends seconds after backgrounding; proximity notifications cease; `CMMotionManager`/`CMDeviceMotion` handlers stop; `Timer`s die. There is no CoreMotion background mode. Locking the screen while the app is frontmost effectively does the same. [SO proximity-in-background](https://stackoverflow.com/questions/14400070/using-proximity-sensor-in-the-background) · [cordova-plugin-proximity#16](https://github.com/awoken-well/cordova-plugin-proximity/issues/16) · [SO CMMotionActivityManager suspended](https://stackoverflow.com/questions/19216169/cmmotionactivitymanager-receiving-motion-activity-updates-while-app-is-suspend)
- ✅ **What survives — retroactive verification**: `CMSensorRecorder.recordAccelerometer(forDuration:)` records 50 Hz accelerometer for up to **12 h**, **"even if your app is suspended or terminated"**, queryable for 3 days (`CMSensorDataList`). Hardware-gated to iPhone 7/7+ and later; needs `NSMotionUsageDescription`/motion authorization. This is the clean answer: start recording at session start, and on resume, replay gravity z to confirm the phone never left face-down. [Apple docs: recordAccelerometer](https://developer.apple.com/documentation/coremotion/cmsensorrecorder) · [WWDC17 session 704 (iPhone 7+, 12–36 h, 3-day retention)](https://devstreaming-cdn.apple.com/videos/wwdc/2017/704rn4fu5zbv1b8s222/704/704_creating_immersive_apps_with_core_motion.pdf)
- ✅ `CMMotionActivityManager.queryActivityStarting` returns historical motion classification (`stationary`, `walking`, `automotive`…) while the app was suspended — corroborating signal; expect several minutes of reporting delay and at least one report of empty results when queried while still backgrounded (query after returning to foreground). [startActivityUpdates docs](https://developer.apple.com/documentation/coremotion/cmmotionactivitymanager/startactivityupdates(to:withhandler:).md) · [SO query-in-background](https://stackoverflow.com/questions/42426665/cmmotionactivitymanager-queryactivitystarting-in-background-with-location-update)
- `CMPedometer` historical step data — weaker corroboration (steps during a "focus" session ⇒ picked up).
- ❌ **Silent push**: throttled, sent at priority 5, "several 1 or 2 per hour across all apps" at best, never guaranteed, and not delivered after force-quit — cannot drive real-time verification. [Apple Forums](https://developer.apple.com/forums/thread/760244) · [TN2265](https://developer.apple.com/library/archive/technotes/tn2265/_index.html)
- ❌ `BGTaskScheduler`/`BGAppRefreshTask`: system picks the timing — periodic at best. [expo-background-task docs](https://docs.expo.dev/versions/latest/sdk/background-task/)
- ⚠️ **Significant-change/visits**: `startMonitoringSignificantLocationChanges` (~500 m granularity) and `CLVisit` (arrive/depart at places) are Apple's recommended low-power alternative — too coarse to detect a lifted phone, but can corroborate "left the building" during a session. [Apple: background execution modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes.md)
- ✅ **DeviceActivity (Screen Time API, iOS 16+)**: a `DeviceActivityMonitor` extension executes on schedule windows and app-usage thresholds **while the host app is suspended** — the sanctioned path to detect "user opened another app during the session". Requires the `com.apple.developer.family-controls` entitlement (Apple must approve for distribution) + user Screen Time authorization. This is what Forest/Flipd/one sec use. [Configuring Family Controls](https://developer.apple.com/documentation/xcode/configuring-family-controls.md) · [WWDC22 Screen Time API](https://developer.apple.com/videos/play/wwdc2022/110336/) · [Streaks walkthrough](https://crunchybagel.com/monitoring-app-usage-using-the-screen-time-api/)
- ⚠️ The old trick of staying alive via `audio` background mode (silent audio) to keep sensors streaming still works technically but is an App Store rejection risk unless the app has a genuine audio feature. [SO background types](https://stackoverflow.com/questions/21380806/receive-accelerometer-updates-in-background-using-coremotion-framework)

## 3. Prior art

- **Dote Timer (dotetimer.com)** — the reference UX: select plan → flip phone → timer starts; "less than 15 seconds are not being recorded"; docs explicitly say "press the power button after turning it over to save battery" — i.e., wall-clock anchored, no continuous sensor verification after lock. Provides a "Touch Timer" fallback "for people who need to use phone". The companion site FAQ reveals a Flutter build (sqflite database). [Tutorial](https://dotetimer.com/dote-timer-tutorial-eng/) · [AI Dote Timer manual](https://aidtimer.com/manual/)
- **Forest (forestapp.cc)** — does **not** use face-down sensors; uses lifecycle + Screen Time API: on iOS 16+ the app-allowlist uses Screen Time permission and opening a non-allowlisted app triggers a full-screen shield; leaving Forest under deep-focus shows a return-notification and the tree dies if you don't return within a few seconds' "save the tree" grace; force-closing the app kills the tree. Their FAQ even notes Face-ID unlocking to the lock screen counts as device use. On Android, deep-focus needs special permissions (usage access). [llms-full.txt](https://www.forestapp.cc/llms-full.txt) · [FAQ: dead trees (iOS)](http://help.forestapp.cc/zh-TW/articles/12750158) · [FAQ: allowlist iOS 16+](http://help.forestapp.cc/zh-CN/articles/12808022)
- **Flipd** — old "Full Lock" hid apps via an **MDM profile**; since iOS 16 they migrated to Apple's Screen Time API (app blocking during Focus Lock). [Flipd FAQ](https://intercom.help/flipdapp/en/articles/7065786)
- **one sec** — not a face-down app but the leading "intervention" pattern: Shortcuts "Open App" automations + Screen Time API (iOS 16+) delayed/immediate interventions. [one sec docs](https://tutorials.one-sec.app/en/articles/3973762) · [their Screen Time API bug notes](https://tutorials.one-sec.app/en/categories/683266)
- **React Native libs**: `react-native-proximity` (iOS+Android, but **archived**, old-arch, last meaningful release 2017); `@lowkeychat/react-native-proximity-sensor` (new-arch capable, niche); `react-native-sensors` (accel/gyro/mag — no proximity). [react-native-proximity GH](https://github.com/williambout/react-native-proximity) · [@lowkeychat on npm](https://www.npmjs.com/package/@lowkeychat/react-native-proximity-sensor)

## 4. React Native / Expo story (task-buddy-mobile: SDK 58, managed CNG, EAS)

- **Works in Expo Go today**: `expo-sensors` `Accelerometer`/`DeviceMotion` → face-down via `accelerationIncludingGravity.z` (sign differs per platform — calibrate at session start); `DeviceMotion.rotation` beta/gamma as alternative. iOS requires `NSMotionUsageDescription` via the `expo-sensors` config plugin (`motionPermission`). `expo-keep-awake` (also in Expo Go) prevents auto-lock so the app can keep verifying — at battery cost. [sensors v58](https://docs.expo.dev/versions/v58.0.0/sdk/sensors/) · [devicemotion v58](https://docs.expo.dev/versions/v58.0.0/sdk/devicemotion/) · [keep-awake v58](https://docs.expo.dev/versions/v58.0.0/sdk/keep-awake/)
- **Not in Expo Go → needs a dev build (`eas build --profile development`)**:
  - iOS proximity (`isProximityMonitoringEnabled`) — no Expo module; custom Expo Modules API native module or a third-party RN lib. (The two RN proximity libs above are stale — a ~50-line custom module is likely cleaner.)
  - Android `TYPE_PROXIMITY` — same; trivial custom module.
  - `CMSensorRecorder` retroactive verification — nothing in Expo SDK; custom iOS module.
  - Android foreground service for screen-off sensing — custom config plugin + native service (or `notifee`-style lib).
  - Screen Time API (`FamilyControls`/`DeviceActivity`) — custom module + `com.apple.developer.family-controls` entitlement (Apple approval) — large scope, defer to a later ticket.
- `expo-background-task` (WorkManager/BGTaskScheduler) is in Expo Go but cadence is ≥15 min and system-chosen — fine for sync, useless for session verification. [background-task](https://docs.expo.dev/versions/latest/sdk/background-task/)

## 5. Graceful degradation

- **Sensor absent/denied**: Android `getDefaultSensor` returns `null` → degrade to orientation-only. iOS: set `isProximityMonitoringEnabled`, re-read — `false` means unsupported (iPad). Every comparable app treats sensors as best-effort: Dote offers the "Touch Timer" as the no-sensor path. [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/uikit.uidevice.proximitymonitoringenabled) · [Dote tutorial](https://dotetimer.com/dote-timer-tutorial-eng/)
- **Session verification tiers** (recommended over pause-vs-fail): `verified` (continuous or retroactively-verified face-down data), `unverified` (wall-clock only — e.g., device locked, Expo Go, iPad), `violated` (lifted/other-app detected). Never hard-fail a session on missing hardware.
- **Cheating tolerance**: both leaders allow slack — Dote ignores <15 s; Forest gives a few seconds to return before the tree dies. Recommend a configurable grace (e.g., 10–15 s of lifted state = pause/warn; sustained lift = mark violated), plus the Dote rule: sessions <15 s aren't recorded. [Forest FAQ](http://help.forestapp.cc/zh-CN/articles/12749731)
- **Power-button locking must not be a fail**: Dote explicitly tells users to lock after flipping. Treat lock as "unverifiable interval", not a violation — on iOS the CMSensorRecorder trace can verify it retroactively anyway.
- **Backend**: client reports `start_ts`, `end_ts`, `verification` tier, `violation_events[]`; server stores raw facts, doesn't trust the verdict — the mobile app can always lie.

## Recommended detection strategy for Task Buddy

- Anchor every session on **wall-clock timestamps** (start = first confirmed face-down); the sensor stream only supplies *verification*, never the elapsed time — this matches Dote's "lock the screen to save battery" model and survives app suspension on both platforms.
- **Minimum viable session (Expo Go, both platforms)**: `expo-sensors` accelerometer/DeviceMotion at ~10–20 Hz while the app is foreground + `expo-keep-awake`; flipping up → pause/violation after a grace window. Zero native work.
- **Face-down rule**: |z| ≈ 1 g with platform-dependent sign (Android −9.8, iOS +9.8 on the gravity/acc z component) plus a dwell time (~0.5–1 s) to reject transient rotations; calibrate the sign once at session start rather than trusting constants.
- **First dev-build milestone**: custom proximity module both platforms — Android `TYPE_PROXIMITY` (wake-up sensor: it still reports covered→uncovered transitions during Doze), iOS `isProximityMonitoringEnabled` (free screen-blank when covered = nice UX).
- **iOS verification while locked/backgrounded**: `CMSensorRecorder.recordAccelerometer` for the session duration (≤12 h) in a custom module; on resume, scan the recording — any non-face-down gravity segment ≥ grace ⇒ violation. This is the only sanctioned API that answers "did it stay down while I was suspended"; flag: iPhone 7+ only, and needs motion permission.
- **Corroborate** with `CMMotionActivityManager` history (`stationary` throughout = good; `walking/automotive` = suspicious) — query after returning to foreground, expect minutes of latency.
- **Android screen-off coverage**: FGS (`specialUse` type, justify on Play) + `PARTIAL_WAKE_LOCK` + proximity listener; accept that accelerometer stalls in deep Doze and rely on the wake-up proximity events + FGS liveness.
- **Anti-cheat (separate phase)**: Android `UsageStatsManager` for foreground-app checks; iOS `DeviceActivity` extension for cross-app detection — both need extra permissions/entitlements, so ship the orientation-only version first.
- **Do not** design for silent-push or background-fetch checks — they're throttled/system-scheduled and can't attest continuity; treat server-side receipt of a "session end" ping as informational only.
- **Unverified sessions are fine to ship**: Dote Timer's actual product is wall-clock + flip UX with a no-sensor fallback; match that, add verification tiers as dev-build milestones land.

### Unverifiable / flagged items

- Exact iOS behavior when the screen is locked *while the app is frontmost* — proximity callbacks appear to continue briefly in some reports but app suspension kills them; safest assumption is "no live events while locked" — needs on-device test.
- Whether `CMSensorRecorder` survives a full device reboot mid-session (docs say "suspended or terminated"; reboot untested) — on-device test needed.
- `queryActivityStarting` empty-while-backgrounded report (SO) is anecdotal; treat historical queries as foreground-only.
- `react-native-proximity` compat with RN 0.88/new-arch is doubtful (archived); prefer a custom Expo module — needs a spike.
